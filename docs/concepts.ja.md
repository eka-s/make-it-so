## 用語集

| 用語 | 意味 |
|---|---|
| 艦長（captain） | 利用者本人。意思決定をする人。エージェントではなく、セッションを持たない |
| クルー（crew） | 艦長と会話し、作業をする AI エージェント。艦ごとに役職（role）を持つ |
| 役職（role） | `ship.yml` で定義するクルーの名前（`first_officer` など。英数字・`_`・`-` で、名前は自由）。コードは役職名を見ない |
| 階級（rank） | `commander`・`chief`・`crew` の 3 種。タスクに関する権限を決める |
| 副長 / commander | 階級が `commander` のクルー。艦長が最初に話しかける相手。艦に 1 人まで |
| 艦（ship） | クルーの編成と、設定・DB の単位。1 つの艦が 1 つのプロセスで動き、専用のポートを持つ |
| 艦隊（fleet） | 艦と名簿をまとめる、艦の外側のディレクトリ |
| 名簿（roster） | 艦隊のクルー候補の一覧（`roster.yml`）。艦の役職に、名簿のメンバーを配属する |
| メンバー（member） | 名簿の 1 人。名前・プロバイダー・人格・個人のルールを持つ。複数の艦に配属できる |
| ミッション（mission） | 会話の入れ物。名前を付けた会話のまとまり。`bridge` が既定 |
| ターン（turn） | 艦長の 1 回の発言に対する、クルー 1 人の、一連の返答 |
| タスク（task） | クルーが、他のクルーに委任する作業の単位 |
| セッション（session） | プロバイダーの AI エージェントとの、1 つの接続（ACP）。会話用とタスク用がある |
| プロバイダー（provider） | クルーを動かす AI の実行環境（`claude`＝Claude Code、`kiro`＝kiro-cli） |
| ACP | Agent Client Protocol。make-it-so がエージェントと話す標準の仕組み（標準入出力の JSON-RPC） |
| 掲示板（MCP board） | クルーがタスクを委任・取得・報告するための内蔵の MCP サーバー（`/mcp`） |
| report | 艦長が副長に出す指示。未報告のタスクの結果を、まとめて報告させる |
| 承認（permission） | クルーがツールの実行許可を求めること。艦長が許可・拒否する |
| ペルソナ（persona） | クルーの口調や性格を決めるプロンプト |
| ブリーフィング | セッションの開始時に、クルーへ送る全文（人格・ルール・スキル・システムの案内） |
| タイムライン（timeline） | 会話の履歴と実行中のものを、画面が描画する単位（`TimelineItem`）に並べたもの |

## 全体像

```
ブラウザ（Web UI）
   │  HTTP / SSE
   ▼
make-it-so サーバー（1 艦 = 1 プロセス、1 ポート）
   ├─ DB（SQLite、艦ごとに 1 ファイル）
   ├─ 掲示板（MCP、/mcp）
   └─ ACP（標準入出力）
        ├─ クルー A（claude / kiro のプロセス）
        ├─ クルー B
        └─ …（SSH 経由のリモートホストのクルーも）
```

- **1 プロセス = 1 艦**です。艦ごとに独立したサーバー（専用ポート・専用の DB）が動きます。複数の艦を同時に動かすときは、艦の数だけプロセスとブラウザのタブを使います（[ガイド](guides/README.ja.md)）。
- クルーは、サーバーのプロセスが子プロセスとして起動する、プロバイダーのエージェントです。サーバー自身はモデルを持たず、エージェントとの橋渡しと、会話の記録・配信をします。
- 画面は、サーバーが返したものを描画するだけです。会話の履歴は DB の 1 か所にあり、画面と他のクルーはそこから読みます。
- **認証はありません。** 自分のマシンで使う前提です（[セキュリティ](security.ja.md)）。

## 階級

階級は、**タスクに関する権限**を決めます。

| 階級 | タスクの発行 | report で扱えるタスク |
|---|---|---|
| `commander` | できる | 艦のすべて |
| `chief` | できる | 自分が発行したもの |
| `crew` | できない | なし |

- 役職の名前は、艦ごとに自由です。階級が同じなら、役職名が違っても同じ権限です。
- 艦長が最初に話しかける既定の相手は、`commander` です。いなければ、`ship.yml` に最初に書いたクルーです。
- クルーに指示を出せるのは艦長だけではありません。`commander` と `chief` は、掲示板で他のクルーにタスクを委任できます。

## ミッション

- ミッションは、**会話の入れ物**です。艦長は、話題ごとにミッションを分けて使います。
- **クルーはどのミッションにも常にいます**（「ミッションの参加者」という概念はありません）。艦長は、どのミッションでも、どのクルーとでも話せます。
- 会話・PIN・承認・モデルの上書きは、ミッションごとに持ちます。クルーのセッションも、ミッションごとに別です。
- 複数のミッションは並行して動かせます。1 つのミッションで同時に動かせるターンは、1 つです。
- アーカイブは、削除ではなく、一覧に出さない設定です。会話は消えません。
- **ミッションの会話は、クルー同士で共有されます。** クルー A に話しかけた内容は、後でクルー B に話しかけたとき、B にも前置きとして伝わります（[ターンの流れ](#ターンの流れ)）。

## セッション

クルーごと・ミッションごとに、別のセッションを持ちます。

| 種類 | 用途 | 寿命 |
|---|---|---|
| 会話用 | 艦長との会話 | 最初に話しかけたときに作り、プロセスが終わるまで使う |
| タスク用 | 委任されたタスクの実行 | 使い捨て。タスクごとに作る |

- 会話用セッションの起動は、プロセスの起動、初期化、セッションの作成、ブリーフィングの送信の順です。
- プロセスが落ちたクルーは、次に話しかけたときに、最初の起動と同じ経路で立ち上がります。クルー自身の記憶には頼らず、**ミッションの会話の記録を DB から作り直して**渡します。
- 艦長は、画面から、クルーのセッションを作り直せます（再起動）。

## ターンの流れ

1. 艦長がクルー宛てにメッセージを送る（`POST /api/crew/:role/message`）。
2. サーバーが、艦長の発言を DB に記録し、ターンを開始する。
3. クルーに送るプロンプトの前に、**ミッションの会話の前置き**を付ける。前置きは、そのクルーがまだ見ていない、ミッション内の発言（他のクルーとの会話を含む）です。セッションを作った直後は直近の部分、続けているときは前回からの差分だけを渡します。
4. クルーの返答が、断片（チャンク）で届く。サーバーは、本文を `TimelineItem`（`status: streaming`）として画面へ配信する。
5. 終わると、返答を DB に記録し、`done` として確定する。
   - 艦長が停止した場合は、途中までの本文を残して「中止」として記録する。
   - 失敗した場合は、「エラー」として記録する。
6. 一時的な失敗（RPC の内部エラー）は、セッションを作り直して、自動で一度やり直す（リカバリ）。艦長が停止したあとの失敗は、エラーにもリカバリにもしない。

プロバイダーのスラッシュコマンド（`/context` など）は、前置きを付けずに、そのまま送ります（[画面の挙動](reference/behavior.ja.md#スラッシュコマンド)）。

## タスクの流れ

タスクは、`commander` か `chief` が、掲示板の `dispatch_task` で、他のクルーに委任する作業です。

1. **発行:** 発行者のセッションが `dispatch_task(agent, task_name, instruction)` を呼ぶ。サーバーは、タスク ID を払い出し、指示を DB に記録して、画面にカードを出す。委任先には、短い通知だけを送る。
2. **実行:** 委任先のクルーが、`get_task` で指示の本文を読み、タスク用のセッションで作業する。進行中の本文は、画面のカードに流れる。
3. **終了:** 完了か失敗を DB に記録し、カードを確定する。
4. **報告:** 艦長が副長に `report` を出すと、副長が `list_unreported_tasks` で、未報告のタスクの結果を読み、まとめて艦長に報告する。その**ターンが正常に終わると**、読んだタスクが「報告済み」になる（報告が途中で失敗したときは、未報告のまま残る）。

- 誰が・どのミッションから呼んだかは、サーバーが各セッションに埋め込んだ識別ヘッダーで判別します。モデルの自己申告には頼りません。そのため、複数のミッションが並行していても、同じクルーへの発行が取り違えられません。
- 「未報告」は、DB の事実（報告の記録がないこと）から求めます。専用の「消す」操作はありません。
- **キャンセル:** 委任先のセッションにキャンセルを送ります。タスクは、**中止までの出力を残して終わり、「中止」の印が付きます**（会話のターンの中止と同じ扱いです）。未報告のタスクとして残り、副長への報告には、「艦長が中止した。出力は途中まで」と添えられます。

## 人格・ルール・スキル

クルーに何を知らせ、どう振る舞わせるかは、次の 4 つで決まります。

| 要素 | 内容 | 注入のしかた |
|---|---|---|
| 人格 | 口調・性格 | `personnel/{ID}.md` を注入する。または、プロバイダー側のエージェント定義（`agent`）に任せる（どちらか一方） |
| ルール | 守ること | ファイルの全文を注入する。メンバー個人のルール、艦のルールの順に連結する |
| スキル | 必要なときに読む手順書 | 名前と説明だけを案内し、本文はモデルが必要なときに読む |
| システムの案内 | 共通の運用ルール、スキル一覧、（発行できる階級には）`dispatch_task` の説明とクルー編成表、担当範囲 | 常に注入する |

- 人格の出どころは、クルー単位で、**人格ファイルか、`agent` のどちらか 1 つ**です。`agent` を指定すると、人格ファイルは注入しません。ルール・スキル・システムの案内は、どちらでも注入します。
- 作業ディレクトリ（`cwd`）の、プロバイダーの設定（`CLAUDE.md` や `.kiro/` など）は、make-it-so の注入とは別に効きます。同じ内容を、ルールに重複して書かないでください。
- **担当範囲（`targets` / `access`）は、プロンプトでの取り決めです。** 「このディレクトリ以外は禁止」という案内を、クルーに送るだけで、技術的な強制はありません（[セキュリティ](security.ja.md)）。プロバイダー固有の権限の仕組みには、個別に対応しない方針だからです。

## モデルの決まり方

クルーが使うモデルは、次の順で決まります（上が優先）。

1. ミッションごとの上書き（画面で変更。新しいミッションには引き継がれない）
2. `ship.yml` の `crew.<役職>.model`
3. `roster.yml` の `crew.<メンバー>.model`
4. 指定なし（プロバイダーの既定）

- セッションの作成直後に適用します。動いているセッションにも、変更した時点で反映します（ターンの途中なら、次のターンから）。上書きを解除すると、元のモデルに戻します。
- 選べるモデルの一覧は、セッションを作るまで分かりません。プロバイダーごとに、最後に分かった一覧を保持するので、再起動直後でも選べます。**インストール直後は、そのプロバイダーのセッションを一度作るまで、一覧が空です。**
- kiro は、モデルの選択肢を返さないため、モデルを変更できません。

## 承認

- クルーがツールの実行許可を求めると、サーバーが保留として記録し、画面に出します。艦長が許可か拒否を選ぶと、クルーへ答えを返します。
- 承認は、どのミッションの、どのクルーのものかを持ちます。画面は、今開いているミッションの承認だけをトレイに出します（[画面の挙動](reference/behavior.ja.md#承認待ち)）。
- 権限モード（`permission_mode`）で、承認を求める範囲を変えられます。値はプロバイダーの設定です（[設定](reference/configuration.ja.md)）。

## プロバイダーの違い

差異は、プロバイダーごとのクライアントに閉じ込め、それ以外のコードにはプロバイダーの分岐を書きません。

| | claude | kiro |
|---|---|---|
| 使用量の単位 | 推定費用（USD）。ACP の累積値から、ターンごとの差分を計算 | 独自のクレジット |
| コンテキスト使用率 | ACP の使用量通知から | kiro 独自の通知から |
| モデルの選択 | できる | できない |
| `agent` の渡し方 | セッション作成後に設定 | 起動引数 |
| 掲示板（MCP）の登録 | セッション作成時に動的に注入（動作確認済み） | 同じ方式（動作確認の範囲は README を参照） |

- Claude Code は、ヘッドレス実行では、ワークスペースの信頼確認が出ません。未信頼のディレクトリでは、`.claude/settings.json` の許可ルールが無視されます。許可リストが効かないときは、ホームの `~/.claude.json` で、そのディレクトリを信頼済みにする必要があります（変更の前に、内容を確認してください）。
- kiro-cli には、ツール呼び出しが実行されないまま本文に漏れる、間欠的な不具合があります。頻発するときは、そのクルーのセッションを再起動してください。

## 設計の方針

- **サーバーに寄せ、画面は薄く。** 複雑なロジックはサーバーに置き、画面は、サーバーが返したものを描画するだけにします。画面が、サーバーの値から推測・変換・再構築しなければならなくなったら、それはサーバー側の設計の不備のサインとして、サーバーで解決します。以前は、複数の経路から個別に組み立てていたため、表示の分断やメッセージの重複が繰り返し起きました。
- **単一のデータソース。** 会話の画面は、1 つのスナップショット（`GET /api/timeline`）と、3 種類の汎用のイベント（`upsert`・`append`・`remove`）から作ります。新しい機能は、まず、この既存のデータを拡張できないかを考えます。
- **履歴は追記のみ。** 会話の履歴は、イベントを足していくだけで、書き換えません。状態の変化も、新しい事実として足します（[データモデル](reference/data-model.ja.md)）。
- **プロバイダーに依存しない。** プロバイダー固有の機能（権限の強制など）には、個別に対応しません。差異は、クライアントの境界に閉じ込めます。
- **依存を渡す。** 設定・外部コマンド・時刻などは、引数で渡します。インポートしただけで副作用のある構成にしません（[アーキテクチャ](architecture.ja.md)）。
