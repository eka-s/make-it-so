# 既知の不具合: kiro-cli でツール呼び出しが実行されず静かに止まる

調査日: 2026-11-06
対象 kiro-cli バージョン: 3.1.0

> **注記（2026-11-06 更新）**: 当初は「新 TUI 固有の不具合で `--classic` 起動で
> 回避できる」と見立てていたが、その後の切り分けで **`--classic` は ACP 経路には
> 効かない**こと、UI/engine/provider/OS いずれにも依存せず確率的に発生することが
> 判明した。本ドキュメントは更新後の結論で全面的に書き直してある。

## 症状

会話・タスク実行の途中で応答が「止まる」。正確には、**モデルが出したツール
呼び出しが実行されないまま、ターンが正常終了（end_turn）扱いで終わる**。

- ツールの承認プロンプトが出ない・実行もされない。
- モデルが返したツール呼び出しマークアップ（`<invoke name="...">` 等）が、
  実行されず**本文テキストとして漏れ出る**。
- round-trip 分の credits だけは課金される。
- **エラーを出さず `end_turn` で正常終了する**ため、アプリ側からは「静かに
  止まった」ようにしか見えない（例外もタイムアウトも発生しない）。
- 書き込み系（ファイル作成・編集）で特に実害が顕在化しやすい（実行されて
  いないのにエラーも返らないため、呼び出し側は「成功した」と誤認する）。

make-it-so の DB（timeline_events / `bridge.db`）側では、この現象は次の形で
記録されていた:
- `turn_completed_events` に**正常完了として記録**され、`text`（本文）に
  ツール呼び出しマークアップがそのまま混入している。
- 承認・実行のイベントが無いまま end_turn。
- `task_error` は全期間 0 件（＝エラーを出さず静かに end_turn している裏付け）。
- 11/06 時点の実データでは、クルー（ensign / chief_engineer / first_officer）
  との直接会話ターンで本文に XML が漏れた例が多数確認された。

### 画面での見分け方（艦長向け）

タイムラインの発話に、次のような**ツール呼び出しマークアップの地の文**が
現れていたら、この現象（リーク）だと判断してよい:

- `<invoke name="shell">` / `<parameter name="...">` といった**生のタグ**が
  応答本文にそのまま表示される。
- `__tool_use_purpose` のような、通常は目に触れない**独自パラメータ名**が出る。
- タグの頭が `con` / `court` のように**崩れたプレフィックス**になっていることがある
  （`<invoke` の直前にゴミ文字が付く）。
- 「〜を実行します」と宣言した直後に実際には何も実行されず、同じ宣言を
  繰り返す（ツールが動いていないため先に進まない）。

これらが見えたら、そのクルーの**セッションを再起動**するのが最も確実な対処
（下記「運用での対処」参照）。

## 原因（確定）

**kiro-cli 本体（v3.1.0）の既知の間欠バグ。** ACP 層・make-it-so のアプリ層
（bridge.ts / base-acp-client.ts 等）は無関係。ツール呼び出しが `tool_call`
として正しくディスパッチされず、本文に漏れたまま `end_turn` してしまう、
kiro-cli のツールパース／ディスパッチ層の間欠的な失敗。

### 非依存性（確率的発生）

切り分けの結果、以下のいずれにも**依存しない**ことが分かった:

- **provider**: kiro / claude いずれでも発生しうる（本件は kiro で確認）。
- **OS**: Windows で確認。OS 固有ではない。
- **engine**: `--agent-engine` を v3 → v2 → v1 と切り替えても再発。
- **UI**: `--classic`（= `--legacy-ui`）は ACP 経路には効かない。ACP は UI
  レイヤーを通らないため、TUI レンダラ起因という当初仮説は該当しなかった。
- **agent / 経路**: 特定のエージェントや特定の呼び出し経路に偏らない。
  当初「特定のクルー以外で多い」と見えたのは単にそのクルーとの会話量が多かった
  だけで、露出量の差。発生率自体は経路非依存。

→ 以上から、**どの軸でも確率的に発生する kiro-cli 本体のバグ**と確定。

### 一致する GitHub issue

本家 **`kirodotdev/Kiro`** に集約 issue がある（`aws/amazon-q-developer-cli`
は旧リポジトリ）:

- **#11771（open・メンテナ調査中）** — 本件の集約 issue。「ツール呼び出しが
  断続的にパース／ディスパッチされず、生のマークアップが本文に漏れて
  end_turn する」。公式に「ツールパース／ディスパッチ層の間欠的な失敗」と
  認定されている。
- 同一バグ群: #8124 / #8654 / #11776 / #11125 / #9180 / #3810 / #3818。
  （#8124 のコメントに、custom agent + 長セッションで断続的に XML が漏れる、
  本件と一致する再現報告がある。）

### ACP 用の回避オプションは存在しない

`kiro-cli acp --help` / `kiro-cli chat --help` / settings / 公式 issue を横断で
確認したが、**ACP モードでこの挙動を抑止する設定オプションは無い**。各報告で
一貫している回復手段は「同じセッションへ `continue` を送ると、次ターンで
ツールが正常に実行される」ことだけ。

## 回避策の検討と結論（`continue` 再送は無効だった）

各報告で一貫していた回復手段は「同じセッションへ `continue` を送ると次ターンで
ツールが実行される」ことだったので、make-it-so でも一度これを実装した（リーク
検出 → `continue` を最大3回まで自動再送）。

**しかし実データ上、`continue` 再送では回復しなかった。** 再送ログ（`app.log`）では、
検出のたびに continue を3回フル再送しても毎回同じリークが返り、上限到達で諦める、
というパターンが繰り返し記録された:

```
[Kiro] Detected leaked tool-call markup (kiro-cli#11771); resending "continue" (attempt 1/3)
[Kiro] ... (attempt 2/3)
[Kiro] ... (attempt 3/3)
[Kiro] Leaked tool-call markup still present after 3 "continue" retries; giving up and returning as-is.
```

いったんこの状態に陥ると `continue` では抜けられない。発生タイミングの傾向
（セッション開始からしばらく経つと頻発する）から、**コンテキストサイズに依存**
していると見られる。再送しても頻発するなら実質的な意味が無いため、**`continue`
再送による回避は撤去した。**

### 試したが効かなかった回避策（記録）

`continue` 再送以外にも、発火条件を狙った緩和をいくつか検討・検証したが、
**いずれも実効性が無かった**。同じ轍を踏まないよう記録しておく:

- **ツール呼び出し前に空行で区切る** — 実機で試行し、効果なし（リークは変わらず発生）。
- **崩れたプレフィックス（`court` / `con` 等）を付けない** — これらは原因ではなく
  リークの**結果（破損の症状）**。付けないよう意識しても発生は防げない。
- **前置きの地の文を短く/ゼロにする、ツール呼び出しを独立したターンにする** —
  「同一ターン内でテキスト→ツール呼び出しへ遷移する瞬間に壊れる」という仮説が
  あり、本文ゼロで即ツール呼びすると成功しやすいという少数回の観察もあった。
  しかし bridge.db の全ターン（会話3081件・タスク421件）で検証したところ、
  **本文長・前置きの有無とリーク率に有意な相関は無かった**（リーク率は会話2.1%
  /タスク2.4%で経路非依存、前置きが短いほうがむしろリーク率はやや高い——これは
  リークで途中で切れて短く記録される見かけ）。加えて、仮に発火条件だとしても
  「ツールは1ターン内で思考しながら複数回呼ぶ」のが本来の動きなので、**前置き
  禁止・ツール単独ターン化は運用に乗らない**（仕事にならない）。

結論として、クルーの振る舞いを縛る方向の回避策はいずれも筋が悪い。**制御可能な
レバーは見つからなかった。**

### 運用での対処

- リークが頻発し始めたら、**そのクルーのセッションを再起動する**（コンテキストが
  浅い起動直後はリークが出にくい、という観察に沿った対処）。これは艦長の運用判断。
- make-it-so 側の自動回復には期待しない。
- あまりにひどい場合は、make-it-so を使わず **kiro-cli を直接使う**。

### コードについて

回避ロジック（`continue` の自動再送）と、それを載せていた拡張点（ターン完了フック
`onTurnCompleted`）は、いずれも撤去済み（2026-11-06）。現状 make-it-so 側に、この
バグ専用のコードは残っていない。

## 今後の対応

- kiro-cli のバージョンアップで #11771 等が修正されたら、本現象自体が解消する
  可能性がある。アップデート時に、リークが発生しなくなったか `app.log` /
  timeline_events で再検証する。
- `--classic` / `--agent-engine` の指定は本件の回避には無効なので、これらを
  回避目的で設定に残さない。
